# 実装工程の考え方

- 設計書と実装が常に一致するようにすること
- 実装の修正が行われるたびに該当の設計書と乖離が出ないよう、都度修正する。
- Pythonはインスタンス状態（`__init__`で保持し続ける値）を持たない処理をクラス化する必要はなく、`auth.py`・`crud.py`・`common.py`のようにモジュールレベル関数として定義する。クラスを使うのは、実際にインスタンス間で状態を保持する必要がある場合のみとする。
- 処理記述書の以下の箇所は実装時にdocコメントとして利用する。それ以外の箇所はdocコメントとして利用しない。
    - 処理概要
    - パラメーター（トップレベルの引数の型と概要のみをdocコメントに記載し、項目単位の条件は設計書側を参照する）
    - 戻り値（トップレベルの戻り値の型と概要のみをdocコメントに記載し、項目単位の条件は設計書側を参照する）
    - 例外処理（エラー条件とエラー内容）
    - 処理フロー（処理詳細の「### 1. ～～」、「### 2. ～～」の箇所のみ順番に記載）

## 作業手順
1. 設計書の確認
2. 実装
    - 設計書のどの処理がどのコードに紐づくか分かるように記載すること
    - ユーザーはシステム作成の知識がないことを前提に、分かりやすくコメントを付与すること
    - docコメントは、実装の着手前に`references/サンプル/docコメント記載例_<言語>.md`（「## 参照資料」の「◆docコメント」参照）を読み、その形式に従って記載すること（必須）。記載例は、`design`スキルのサンプル処理記述書（復習項目更新）をもとに、docコメントの記載形式のみを示したものである（レイヤー構成は本サンプルの対象外）。
    - 記載例のない言語（TypeScript等）も、その言語のdocコメント記法（TypeScriptでは`/** */`）の中に、記載例と同じ項目・見出し（クラス・ファイル・関数グループ・関数ごとの項目、【処理概要】等）で記載すること。言語標準のタグ形式（TSDocの`@param`等）には置き換えない。記法の近い言語の記載例（TypeScriptでは`docコメント記載例_java.md`）を手本とする。
3. チェックリストを確認し、問題があればレビュー工程前なのでそのまま修正可能。
4. 実装レビュー工程
    - `運用ルール/開発ルール/レビュー工程ルール.md`に従う。

## アーキテクチャ
- ビジネスロジック（状態遷移・オーケストレーション・外部API呼び出し等の「処理」）を担うレイヤーと、内部の業務コンテンツモデル（データ構造）を担うレイヤーは分離し、API入出力用DTOとも区別する。レイヤーの実体（ディレクトリ名・パッケージ名等）は各言語・フレームワークの慣習に従う。
- レイヤー間の呼び出しは、エンドポイント層→オーケストレーション層→データアクセス層／共通処理／業務コンテンツモデル層の一方向のみとし、下位レイヤーから上位レイヤーを呼び返さない。エンドポイント層は下位レイヤーを直接呼び出さず、必ずオーケストレーション層を経由する。
- 複数の処理段階を内部に持つ共通処理（生成AI呼び出し・自己レビュー等）は、責務ごとに独立したモジュールへ分割し、外部へ公開する窓口の関数を1つに絞る。内部の各段階は非公開関数として隠蔽し、呼び出し元が内部の呼び出し段数を意識しなくてよい状態を保つ。

## コーディング規約
- 引数に対して、関数を直接埋め込まず、変数として取得してから設定する。
- 無名関数（Pythonでは`lambda`）は、`sorted(users, key=lambda user: user.name)`のように処理が非常に短く、名前を付けても意味が増えない場合にのみ使用する。
- 以下のいずれかに該当する場合は、無名関数を使わず名前付きの関数（関数内関数を含む）にすること。
    - 関数呼び出しが複数行になる
    - 引数が多い
    - 同じ種類のラムダが複数ある
    - 初回生成と修正処理で役割が異なる
    - デバッグ時に処理単位で追いたい
- 関数名は処理を端的に表し、処理内容を見なくても関数名で分かることを理想とする。
