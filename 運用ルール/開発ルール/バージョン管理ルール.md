# バージョン管理ルール

バージョンは`MAJOR.MINOR.PATCH`の3桁で表記し、次の2種類を独立して管理する。

| 種類 | 付与先 | 上がるタイミング |
|---|---|---|
| 成果物のバージョン | 成果物のファイル名 | レビュー指摘対応完了時・再鑑完了時 |
| システムのバージョン | gitタグ（`main`の該当コミット） | `main`へマージするPR（リリースPR・Hotfix PR）の単位 |

- システムのバージョンは、[セマンティック バージョニング 2.0.0](https://semver.org/lang/ja/)（以下「SemVer」）に従う。
- 成果物のバージョンは、同じ3桁表記を用いたhojou独自のバージョン管理方式とする（SemVerには準拠しない）。
- システムのバージョンの番号は`MAJOR.MINOR.PATCH`（例：`1.3.0`）であり、SemVer上、接頭辞`v`は番号に含まれない。gitタグ名には、慣習に従い接頭辞`v`を付けた`vMAJOR.MINOR.PATCH`（例：`v1.3.0`）を用いる。本ルールおよび他の資料中の「システムv1.3.0」等の表記は、このタグ名、またはそのタグが指すバージョンを表す。
- 両者の番号は一致させない（例：システムv1.3.0の時点で、`ユーザー管理仕様書_v2.2.0`・`DB設計書_v1.7.3`が並存してよい）。
- 両者の対応関係は、システムのバージョンのgitタグが指すコミットのツリーで一意に決まる（「## システムのバージョン」参照）。

## 対象

要件定義書・設計書・単体テスト仕様書・結合テスト仕様書など、レビュー工程を経て確定していく成果物に適用する。

- 引継ぎ資料は独自のバージョン管理方式（[引継書ルール](../引継書ルール/引継書ルール.md)のbk/退避方式）に従うため対象外。
- レビュー指摘表はレビュー対象成果物のバージョンに紐づくファイル名（例：`設計書生成_v0.1.0_レビュー指摘表.md`）とし、指摘表自体には独立したバージョンを付与しない。指摘表のファイル名のバージョンは、レビューを開始した時点の成果物のバージョンとし、指摘対応によるバージョンアップでは変更しない。

## バージョン表記

- 表記は`MAJOR.MINOR.PATCH`の3桁とする。各桁は非負整数とし、先頭ゼロは付けない（`v01.2.0`は不可）。
- プレリリース識別子（`-alpha`等）・ビルドメタデータ（`+build`等）は使用しない。
- 成果物はファイル名にバージョンを付与する。

```
<成果物ファイル名>_vMAJOR.MINOR.PATCH.md
```

## 互換性の考え方

hojouでは、バージョンの上げ幅を判断するため、成果物およびシステムごとに互換性管理対象を定義する。

| 対象 | 互換性管理対象 | 後方互換性が保たれている状態 |
|---|---|---|
| 成果物 | 成果物に定義された仕様（項目・処理・条件・インターフェース等） | 既存の下流成果物（設計・実装・テスト仕様書等）を修正しなくても整合性が維持される |
| システム | 利用者・連携先が依存する外部仕様（画面・API・データ形式・設定形式等） | 既存利用者や連携先で追加対応・変更対応を行わなくても従来どおり利用できる |

- システムの互換性管理対象は、SemVerにおける公開APIに対応する。
- 下流成果物とは、要件定義書 → 設計書 → 実装・テスト仕様書の順で、上流の成果物に依存する側の成果物を指す。
- **判定原則：変更の理由（誤記・バグ等）ではなく、変更後の互換性で判定する。** 誤りの修正であっても、互換性管理対象の仕様が変わり下流の修正が必要になる場合は、後方互換を壊す変更として扱う。

### 成果物の判定例（設計書の場合）

再鑑完了時に、MAJORとMINORのどちらを上げるかの判定に用いる。

| 上げ幅 | 設計書での例 |
|---|---|
| MAJOR | 項目の削除、型の変更、必須項目の追加、処理の戻り値の変更、入力の上限値の引き下げ（例：最大100件→最大50件。誤記の訂正であっても、下流の実装・テストの修正が必要になる） |
| MINOR | 任意項目の追加、新しい処理の追加、仕様上の意味を変えない誤記修正・表記修正・説明改善（既存の下流は修正不要） |

## システムの桁の意味

システムのバージョンはSemVerに従い、次のとおり上げる。

| 桁 | 意味 | 例 |
|---|---|---|
| MAJOR | 後方互換を壊す変更（大小を問わない） | v1.4.2 → v2.0.0 |
| MINOR | 後方互換のある機能追加、および互換性管理対象の非推奨化 | v1.4.2 → v1.5.0 |
| PATCH | 後方互換のあるバグ修正のみ | v1.4.2 → v1.4.3 |

- MINORを上げる際はPATCHを0に、MAJORを上げる際はMINOR・PATCHを0にリセットする。
- 軽微でも機能追加を含む場合はMINORを上げる（PATCHに含めない）。

## 成果物のバージョン

### 桁の意味

成果物では、PATCHを「レビュー中の中間版」、MINOR・MAJORを「レビューサイクル完了による確定版」として扱う。

| 桁 | 意味 |
|---|---|
| MAJOR | 再鑑完了時に、後方互換を壊す変更を含む場合に上げる |
| MINOR | 再鑑完了時に、後方互換を壊す変更を含まない場合に上げる（誤記修正のみの場合も含む） |
| PATCH | レビュー中の中間版。指摘対応完了時・再鑑での追加修正の完了時に上げる |

- 確定版のPATCHは常に0とする（`vX.Y.0`）。`vX.Y.1`以降は、レビューサイクル中の版を表す。
- 指摘対応の内容がMINOR相当かPATCH相当かを、個別に判断する必要はない。指摘対応の完了時は常にPATCHを上げ、確定時に互換性でMAJOR・MINORを判定する。
- MINORを上げる際はPATCHを0に、MAJORを上げる際はMINOR・PATCHを0にリセットする。

### バージョンアップのタイミング

| タイミング | バージョン操作 |
|---|---|
| 成果物の新規作成（v1.0.0未到達） | `v0.1.0`で作成する |
| レビュー指摘対応完了 | PATCHを+1（例：v0.1.0 → v0.1.1、v2.1.0 → v2.1.1） |
| 再鑑で追加修正が必要になり、その対応が完了 | PATCHを+1（例：v0.1.1 → v0.1.2） |
| 再鑑完了（後方互換を壊さない） | MINORを+1しPATCHを0にリセット（例：v0.1.2 → v0.2.0、v2.1.2 → v2.2.0、v0.9.1 → v0.10.0） |
| 再鑑完了（後方互換を壊す。v1.0.0到達後のみ） | MAJORを+1しMINOR・PATCHを0にリセット（例：v2.1.2 → v3.0.0） |
| プロジェクト完了（初回開発、v1.0.0未到達の場合のみ） | 現在のバージョンをv1.0.0にする |

- 確定済みの成果物を改修する場合は、着手時にバージョンを上げず、指摘対応が完了した時点でPATCHを上げる（例：確定版`v2.2.0`を改修し、指摘対応完了で`v2.2.1`）。
- 指摘対応中の作業途中の状態はgit履歴で管理し、ファイル名のバージョンは上げない。
- 成果物のバージョンは、v1.0.0到達前・到達後で同じ運用とする。

例（v1.0.0到達後）：

```
ユーザー管理仕様書_v2.1.0（確定版）
  →（改修のレビュー指摘対応完了）→ _v2.1.1
  →（再鑑で追加修正、その対応完了）→ _v2.1.2
  →（再鑑完了。後方互換のある仕様追加のためMINOR+1）→ _v2.2.0（確定版）
```

例（v1.0.0到達前）：

```
設計書生成_v0.1.0（新規作成）
  →（指摘対応完了）→ _v0.1.1
  →（再鑑完了）→ _v0.2.0
```

### v1.0.0 到達前（初期開発）

SemVerのMAJOR 0（初期開発）の考え方を援用し、何が変わってもよい段階として互換性は保証しない。このため、v1.0.0到達前の再鑑完了は、常にMINORを+1する（`v0.9.0`の次は`v0.10.0`とし、MINORの上限は設けない）。

- `v0.x.0`から`v1.0.0`への更新は**プロジェクト完了時のみ**行う。
- 成果物の`v1.0.0`は、その成果物単体の承認時点ではなく、hojouにおける初回プロジェクト完了版を表す（要件定義書が先に承認済みでも、プロジェクト完了までは`v0.x.0`のままとする）。
- 「プロジェクト（結合テストあるいはシステムテスト）完了」のタイミングで、v1.0.0未到達の成果物を`v1.0.0`にする（初回開発時のみ。v1.0.0到達後の改修完了時にv1.0.0へ戻すことはない）。この作業は`project-completion`スキルの作業手順に含まれ、プロジェクト完了の定義（README・機能別引継ぎ資料・成果物のv1.0.0更新・完了チェックリスト）に従う。

### 不変性

- 確定版（`vX.Y.0`）の内容は、バージョンを上げずに変更しない。確定後の変更は、指摘対応完了時にバージョンを上げて出す。
- 成果物の各バージョンは、旧バージョンのファイルを削除して1つだけ存在させる（旧版はgit履歴で保持する）。バージョンを上げる際は、ファイル名を変更する（リネーム）。

### 成果物間の参照表記

- 成果物間の参照（リンク・ファイル名の記載）には、バージョンを含めない。バージョンアップのたびに、下流成果物の参照表記の更新が必要になることを避けるため。
- 相対リンクを使う場合は、バージョンを含まないパス（格納フォルダまで）を指定し、バージョン付きのファイル名は指定しない。
- 参照先の成果物は、バージョンを含まない論理名と、成果物内の見出しで特定する（例：要件定義書「ユーザー登録」）。

## システムのバージョン

- 付与先はgitタグとし、`main`の該当コミットに付与する。タグ名は`vMAJOR.MINOR.PATCH`とし、付与後にリモート（`origin`）へpushする（付与のタイミング・手順は[ブランチルール](../GitHubルール/ブランチルール.md)に従う）。
- タグ（システムのバージョン）はv1.0.0から付与する。v1.0.0より前にはシステムのバージョンを付与しない。
- `main`へマージするPR（`dev`からのリリースPR、およびHotfixのPR）の単位で上げる。成果物のバージョンが上がったタイミングとは限らない。
- 上げ幅（MAJOR・MINOR・PATCH）は、上記「システムの桁の意味」の基準を目安に**人が判断する**。AIは上げ幅を提案してよいが、必ずユーザーに判断させ、AIが独断で決定・付与してはならない。
- 一度付与したタグは、付け替え・削除・移動をしない。内容を変える場合は新しいバージョンとして出す。

### 成果物のバージョンとの対応

- タグが指すコミットのツリーを見れば、そのシステムのバージョン時点の各成果物のバージョンを完全に再現できる（`git ls-tree -r <タグ>`等で確認する）。この再現性は、次の前提で成り立つ。
    - 成果物の各バージョンが1つだけ存在すること（旧バージョンのファイルが並存していないこと）。
    - タグが動かないこと。
    - `main`に未リリースの内容が混ざらないこと（`dev`からは、リリースPR経由でのみ取り込む）。
- 成果物のバージョン一覧を別途管理しない（二重管理によるずれを避けるため）。

```
システム v1.3.0（コミットDにタグ）
├─ 要件定義書_v1.5.0
├─ ユーザー管理仕様書_v2.2.0
├─ DB設計書_v1.7.0
└─ API仕様書_v3.1.0
```

## バージョンアップの考え方

- 成果物のバージョンは開発者向けである。レビューサイクルの経過（指摘対応完了・再鑑での追加修正）と確定状態（再鑑完了）を識別できるよう、レビューサイクルの節目で上げる。
- システムのバージョンは利用者向けである。利用者が追随すべき単位（公開単位）を示すため、`main`へマージするPRの単位で上げる。
