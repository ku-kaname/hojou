# 結合テスト チェックリスト

各項目には`[IT-CHK-01]`〜`[IT-CHK-29]`の固定IDを付与している。AIによる結合テスト生成の自己レビューでは、このIDにより後述の○判定範囲分類・生成対象分類で「どちらの成果物（仕様書／コード）を対象とするか」「全体を俯瞰しないと判定できないか、テストケース1件のみで判定できるか」を判定し、生成対象ごとの自己レビューサイクルで二段構成のチェックを行う。IT-CHK-01（ファイル名一致）のみ、テスト仕様書のファイル名に相当するhttpメソッド・エンドポイントをシステム側が対象エンドポイント抽出結果から機械的に設定する運用の場合、AIの自己レビューサイクルには含めない（詳細は○判定範囲分類・生成対象分類参照）。人手によるレビュー（レビュー指摘表運用時の目視確認等）で用いる場合はIDを意識する必要はなく、そのままチェックリストとして使用してよい。

## テスト仕様書作成

### ファイル管理
- [ ] [IT-CHK-01] テスト仕様書のファイル名が設計書の機能名と一致しているか（表記ゆれに注意：「登録」「作成」、「削除」「情報削除」等）

### テストケースの網羅

**バリデーション異常系**
- [ ] [IT-CHK-02] 必須パラメータが欠落した場合のバリデーションエラーテストケースを作成しているか
- [ ] [IT-CHK-03] 型不一致・桁数オーバーの場合のバリデーションエラーテストケースを作成しているか

**実装の挙動確認**
- [ ] [IT-CHK-04] パスパラメータ・クエリパラメータ等がエンドポイントで正しく受け取られているか確認し、受け取られていない場合の挙動（無視される等）を確認するテストケースを作成しているか
- [ ] [IT-CHK-05] 実装コードの条件分岐を全て確認し、全分岐にテストケースが対応しているか

**前提条件**
- [ ] [IT-CHK-06] テストの有効性を保証するために必要なデータが前提条件に全て記載されているか
  - 例：「自分のデータのみ返却される」を確認するテストでは「他のユーザーデータが存在すること」を前提条件に明記する

**エラーメッセージ**
- [ ] [IT-CHK-07] エラーメッセージの文言は実装コードから確認しているか（推測で記載しない）

### アサーション
- [ ] [IT-CHK-08] 想定結果に記載した全フィールドについて値まで確認するアサーションを実装しているか（フィールドの存在確認のみにしない）
- [ ] [IT-CHK-09] フィルタリング・絞り込みが正しく動作しているか確認するテストに、フィルタ対象外のデータが存在していることをアサーションしているか

## テストコード実装

- [ ] [IT-CHK-10] テスト仕様書の想定結果と、テストコードのアサーションを1フィールドずつ照合したか
- [ ] [IT-CHK-11] エラーメッセージ・ステータスコードの確認は実装コードと突き合わせて記述したか

## HTTPステータスコードの規約確認

- [ ] [IT-CHK-12] 認証エラー時の想定ステータスコードが、認証情報自体が提示されていない場合は401、認証済みだが権限不足の場合は403という規約と一致しているか
- [ ] [IT-CHK-13] 新規リソース作成系エンドポイント（POST）の成功時想定ステータスコードが、RESTの慣例に従い201になっているか（200のまま放置していないか）
- [ ] [IT-CHK-14] 1機能でHTTPステータスコードの誤りが見つかった場合、同種のパターン（認証必須の全エンドポイント・作成系の全エンドポイント）を持つ他の全ファイルを横断的に確認したか

## 正常系テストの検証深度

- [ ] [IT-CHK-15] 正常系のテストケースを作成する際、ステータスコードの確認だけで完了とせず、レスポンス本文の必須項目とDB永続化内容の両方を検証項目に含めたか
- [ ] [IT-CHK-16] APIのレスポンススキーマに必須項目が定義されている場合、その項目が実際にレスポンスへ含まれているかをテストケースの標準観点として組み込んだか
- [ ] [IT-CHK-17] ファイルアップロード・データ登録系のエンドポイントでは、処理が成功したことに加えて「登録された内容が入力値と一致するか」をDBへの問い合わせで確認したか

## 実配線の検証範囲

- [ ] [IT-CHK-18] 結合テストでモックを使う場合、モックの範囲を最小限（外部サービス呼び出し等）にとどめ、アプリケーション内部の実際の呼び出し経路は極力実配線のまま検証したか
- [ ] [IT-CHK-19] モジュール全体をモックする結合テストが、本当に結合テストとして機能しているか（内部の配線を経由しているか）作成時に確認したか
- [ ] [IT-CHK-20] 複数工程・複数コンポーネントにまたがる一連フローの結合テストは、フロー全体を最後まで検証しているか、途中で打ち切られていないか確認したか

## 入力値バリデーションのテスト観点

- [ ] [IT-CHK-21] 入力値バリデーションのテストケースを作成する際、「未指定」「上限超過」「下限（空文字等）」「型不一致」「必須パラメータ完全欠落」を標準の観点として、全エンドポイントへ機械的に適用したか
- [ ] [IT-CHK-22] 同じ論理データを複数の入力経路（直接入力・ファイルアップロード等）で受け付ける場合、経路ごとに同じ検証観点（上限・空値・文字コード等）を適用しているか確認したか
- [ ] [IT-CHK-23] ある入力値検証観点の抜けが1つのエンドポイントで見つかった場合、同じ観点が他の全エンドポイントの仕様書でも検証されているか横断的に確認したか

## 同時実行制御・異常系の網羅

- [ ] [IT-CHK-24] 外部API依存・長時間処理という特有のリスクを持つ機能群では、「並行実行」「失敗後の状態」「再開・再試行」を標準の異常系テスト観点として結合テスト仕様に組み込んだか

## テスト仕様書とテストコードの対応関係

- [ ] [IT-CHK-25] テストコードを新規作成する際、対応する結合テスト仕様書が既に存在することを確認したか（仕様書に記載のケースIDとテストコードを1対1対応で保つ）

## 実装側の変更への追随確認

- [ ] [IT-CHK-26] ファイル構成再編（services層・routers層への切り出し等）を行った際、影響を受ける結合テストのモックパスをすべて更新したか
- [ ] [IT-CHK-27] 処理フローの段階分割（1機能→2機能等）が発生した際、その処理を通しで検証しているテストヘルパー・アサーションを更新したか
- [ ] [IT-CHK-28] AI呼び出しの方式変更（非ストリーミング→ストリーミング等）が発生した際、モックフィクスチャが変更後の呼び出し方式に対応しているか

## フォルダ構成再編時の引き継ぎ確認

- [ ] [IT-CHK-29] フォルダ構成の再編でテスト仕様書を作り直す際、旧版で既に指摘・修正済みだった規約（HTTPステータスコード等）を新版へ引き継いだか

## ○判定範囲分類・生成対象分類

各チェック項目が、(a) 結合テスト仕様書とテストコードのどちらの自己レビューサイクルで使用するか（生成対象）、(b) 生成済みテストケースのうち何件を俯瞰すれば判定可能か（判定範囲分類）を示す分類。新規追加するチェック項目は、この表に両分類を追加登録することで自動的に絞り込み対象へ反映される（単体テスト_チェックリスト.mdの○判定範囲分類・生成対象分類と同じ考え方）。

| IT-CHK-02 | 仕様書 | 全体 | 必須パラメータ欠落ケースの過不足確認は、対象エンドポイントの生成済み全テストケースを俯瞰しないと判定できない |
