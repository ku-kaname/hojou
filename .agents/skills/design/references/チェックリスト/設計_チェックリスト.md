# 設計 チェックリスト

## API・インターフェース設計

- [ ] データ取得・削除系の操作にリクエストボディを持たせていないか（HTTP慣習）
  - 識別子はURLパスパラメータ（例：`/users/{user_id}`）で受け取る
  - リクエストボディを使う場合は登録・更新系のメソッドを選択する
- [ ] 機能名がAPI設計書・設計書ファイル名・テスト仕様書ファイル名で統一されているか

## レイヤー構成

- [ ] ヘルスチェック（疎通確認のみを行う処理）以外の処理で、エンドポイント層から下位レイヤー（データアクセス層等）を直接呼び出していないか。単純な参照等も、オーケストレーション層を経由しているか（アーキテクチャ方針で設けた例外・処理記述書の呼出先を含めて確認する）

## 引数・バリデーション設計

- [ ] 引数定義表にバリデーションエラー時のレスポンス（HTTPステータスコードとメッセージ）を記載しているか
- [ ] 引数の型・最大桁・最小桁を設計書のバリデーションエラー表に記載しているか
- [ ] 引数を変更した場合（例：リクエストボディ→パスパラメータ）、バリデーションエラー表も更新しているか

## レスポンス設計

- [ ] 正常系・異常系それぞれのステータスコードとレスポンスフィールドを網羅しているか
- [ ] エラーメッセージの文言を具体的に記載しているか（実装時に推測で記述しないようにする）

## 横展開確認

- [ ] 設計を変更した場合、同じ構造を持つ他の機能への横展開が必要ないか確認したか
  - 例：ある共通処理の修正 → 同様の構造を持つ全機能に適用
- [ ] ある処理の引数・スキーマを拡張した場合、その処理の呼び出し元・呼び出し先（DBアクセス層・テーブル定義書を含む）すべてに同じ拡張を反映したか（呼び出しチェーンを最後まで辿る）
- [ ] 複数機能から共有される共通処理の説明文・利用機能一覧に、新機能を追加するたびに当該機能を追記したか
- [ ] 既存の指摘・修正を1機能に適用した際、同じパターンを持つ並行機能（段階的に横展開しながら作成している機能群）にも同じ修正が必要ないか確認したか
- [ ] 機能を廃止・変更した場合、その機能への言及が残っている設計書・チェックリスト等が他にないか確認したか

## 類似機能・旧版文言の踏襲時の確認

- [ ] 類似の既存機能の設計書を土台に新機能の設計書を作成する場合、踏襲する文言・手順番号・項目定義が新機能の構成（サービスクラス切り出しの有無、スキーマ構成の違い等）でも成立するか個別に確認したか
- [ ] 踏襲元の機能に存在する項目（責務説明フィールド等）が、新機能でも実際に生成・設定される値か確認したか（実際には生成されない項目をスキーマ定義に残さない）
- [ ] 「進捗保存・再開」等のチェックポイント機構を記述する際、実際に成果物登録処理が完了する手順番号を実装/設計本文と突き合わせたか
- [ ] 文中で参照する手順番号・ファイル名が、踏襲先の新しいファイルでも実際に存在する参照先か1つずつ確認したか（本ファイルの外側の処理を説明する場合は、実体のない手順番号を付けず処理の主体だけを明記する）
- [ ] 並行して設計している複数の類似機能間で、同じ論点について判断がばらついていないか（一方は正しく反映できているのに他方は旧版のままになっていないか）横断的に見比べたか

## ドキュメントの鮮度確認

- [ ] 実装・仕様を変更した際、その処理の実際の内部変数名・格納先を設計書の記述と突き合わせたか
- [ ] 過去に廃止した処理・プロンプトへの言及が、他の設計書の概要説明に残っていないか確認したか
- [ ] 実装工程でセキュリティ対策・入力検証・エラーハンドリングを追加した場合、実装のみで完結させず、対応する設計書（処理詳細・バリデーションエラー表・セキュリティ考慮事項）へ同じタイミングで反映したか
- [ ] 新規エンドポイントを1つ追加する際、影響する設計書（スキーマ定義書・エンドポイント一覧・API通信設計・レイヤー構成のエンドポイント総数等）を一覧化し、1つずつ反映済みか確認したか
- [ ] 設計書と実装コードの突合せを工程完了時だけでなく定期的に行い、「実装が設計より先に進んでしまった」ケースを早期に検知したか

## 言語・フレームワーク固有の考慮

- [ ] テキスト解析ロジックを設計する際、対象言語の記法が複数行にまたがるケース（Pythonの複数行関数シグネチャ等）を考慮したか

## 情報の重複管理

- [ ] 許容値・列挙値などテーブル制約に由来する情報を複数の設計書に文言として複製せず、可能な限り「一次情報を参照」という記載に統一したか
- [ ] やむを得ず複製する場合、一次情報のファイルに「この値を参照している設計書一覧」を明記し、値を変更する際の更新対象チェックリストとして機能させたか
- [ ] 新しい機能を追加する際、既存の列挙型情報（許容値・対象一覧）を持つ全設計書を横断的に検索し、追加すべき値がないか確認したか

## ヘッダーブロックの確認

- [ ] 処理記述書を新規作成する際、ヘッダーブロックの必須4項目（工程・作成者・作成日・最終更新日）を満たしているか。最終更新日は作成日と同一でも省略せず記載したか
- [ ] 同一文言の指摘が複数ファイルに及んだ場合、個別修正だけでなく、テンプレート・生成手順側に構造的な欠陥がないか遡って確認したか

## バージョン管理の確認

- [ ] 設計書をバージョンアップ（v0.1.0→v0.2.0等）した際、旧バージョンファイルの削除まで完了したか（フォルダに新旧ファイルが並存していないか）
- [ ] 設計書・テスト資産から他の成果物への参照（リンク・ファイル名の記載）に、バージョンを含めていないか（バージョン付きファイル名・バージョン表記ではなく、論理名と見出しで特定しているか）
- [ ] 実装ファイルの分割・移設（責務分割等）を行う際、影響するテストコード・テスト仕様書のヘッダー欄（テスト対象ファイル等）を機械的に洗い出したか
- [ ] 過去に一度参照の同期を行った実績があっても、「前回対応済みだから今回は大丈夫」という前提を置かず、改訂のたびに参照側の再検索をゼロから行ったか

## 認証・認可設計

- [ ] 認証フロー全体（認証基盤が行う処理を含む）を把握した上で、各機能の認可処理を設計しているか
  - 認証層でブロック済みの条件を個別機能で二重に実装しないよう留意する
