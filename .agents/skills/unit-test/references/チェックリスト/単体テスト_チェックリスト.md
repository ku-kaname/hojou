# 単体テスト チェックリスト

各項目には`[UT-CHK-01]`〜`[UT-CHK-22]`の固定IDを付与している。AIによる単体テスト生成の自己レビューでは、このIDにより後述の○判定範囲分類・生成対象分類で「どちらの成果物（仕様書／コード）を対象とするか」「全体を俯瞰しないと判定できないか、テストケース1件のみで判定できるか」を判定し、生成対象ごとの自己レビューサイクルで二段構成のチェックを行う。人手によるレビュー（レビュー指摘表運用時の目視確認等）で用いる場合はIDを意識する必要はなく、そのままチェックリストとして使用してよい。

## テストケース設計

- [ ] [UT-CHK-01] 設計書の全条件分岐に対応するテストケースが存在するか
- [ ] [UT-CHK-02] 正常系・異常系それぞれのケースが網羅されているか
- [ ] [UT-CHK-03] モックの呼び出し有無を確認するテストを作成した場合、対称となる逆ケースにも同様のアサーションを追加しているか

## アサーションの粒度

- [ ] [UT-CHK-04] レスポンスの全フィールドについて、「存在する」だけでなく「値が正しい」ことまで確認しているか
- [ ] [UT-CHK-05] レスポンスのフィールドとスキーマ定義を1対1で突き合わせてアサーションを記述しているか

## テストコードの品質

- [ ] [UT-CHK-06] テスト対象のメソッド名・関数名がテストコード内と一致しているか（設計書との乖離に注意）
- [ ] [UT-CHK-07] テスト共通処理（フィクスチャ・ヘルパー等）は共通モジュールに集約しているか

## 対象選定の網羅性

- [ ] [UT-CHK-08] 単体テスト対象の選定基準（分岐数・ネスト階層・再帰の有無等）を全実装ファイルへ機械的に適用し、目視のみに頼らず対象一覧を洗い出したか
- [ ] [UT-CHK-09] 実装工程のレビューで指摘・対応された処理（セキュリティ対策・境界値検証・排他制御等）について、対応する単体テストが存在するか別途確認したか

## 設計変更・実装変更への追随

- [ ] [UT-CHK-10] 呼び出し対象メソッドの引数拡張に伴い、既存テストケースの呼び出し値・想定結果を更新したか
- [ ] [UT-CHK-11] 新しく追加された引数・分岐の効果を検証する新規テストケースを追加したか
- [ ] [UT-CHK-12] 対応設計書リンクが、バージョンを含まないパス（格納フォルダまで）と、論理名・見出しで設計書を特定できているか（バージョン付きファイル名を指していないか）
- [ ] [UT-CHK-13] 関数のシグネチャ・戻り値型を変更した際、対応するdocstring・型ヒントも同じコミットで更新したか
- [ ] [UT-CHK-14] モジュール冒頭docstringの参照設計書が、バージョンを含まない論理名・見出しで記載されているか

## テスト仕様書とテストコードの対応関係

- [ ] [UT-CHK-15] テストコードを新規作成する際、対応する単体テスト仕様書が既に存在することを確認したか（仕様書に記載のケースIDとテストコードを1対1対応で保つ）
- [ ] [UT-CHK-16] テストコードヘッダーの「テスト対象ファイル」欄が、責務分割等で移動済みの実装ファイルではなく現行の実装ファイルを指しているか

## 範囲を対象とするテストケースの設計

- [ ] [UT-CHK-17] 除去・判定対象が「範囲」（複数文字・複数値にわたる区間）である場合、対象が数値の大小比較（境界値分析で両端の検証が有効）なのか、個々の要素を独立に判定する処理（範囲内の全要素の検証が必要）なのかを区別したか
- [ ] [UT-CHK-18] 個々の要素を独立に判定する処理を対象とする場合、テストの入力に範囲の両端だけでなく中間値（複数点、または全要素）を含めたか

## セキュリティ対策テストの網羅性

- [ ] [UT-CHK-19] セキュリティ対策のテストケースを作成する際、「文字列としての完全一致」だけでなく「実行環境（OS・ファイルシステム等）が同一とみなす表記のゆれ」まで踏み込んで検証観点を洗い出したか
- [ ] [UT-CHK-20] 同じ脅威クラス（パストラバーサル等）に対する複数の関数を実装する場合、1つの関数で得られたテスト観点は残りの関数へ横展開して確認したか

## テストケース記載の表記

- [ ] [UT-CHK-21] Markdown表のセル内で、検証対象の文字自体が表の制御文字（`|`）と一致する場合、コード記法の有無にかかわらず`\|`へエスケープしたか
- [ ] [UT-CHK-22] 表を含む成果物を作成・修正した際、実際にレンダリングして列数が意図通りになっているかを確認したか

---

## ○判定範囲分類・生成対象分類

各チェック項目が、(a) 単体テスト仕様書とテストコードのどちらの自己レビューサイクルで使用するか（生成対象）、(b) 生成済みテストケースのうち何件を俯瞰すれば判定可能か（判定範囲分類）を示す分類。新規追加するチェック項目は、この表に両分類を追加登録することで自動的に絞り込み対象へ反映される（実装_チェックリスト.mdの○判定範囲分類と同じ考え方）。

| ID | 生成対象 | 判定範囲分類 | 説明 |
|---|---|---|---|
| UT-CHK-01 | 仕様書 | 全体 | 設計書の全条件分岐との網羅確認は、対象メソッドの生成済み全テストケースを俯瞰しないと判定できない |
| UT-CHK-02 | 仕様書 | 全体 | 正常系・異常系の網羅確認は、対象メソッドの生成済み全テストケースを俯瞰しないと判定できない |
| UT-CHK-03 | コード | 全体 | 対称となる逆ケースの有無確認は、複数のテスト関数を突き合わせないと判定できない |
| UT-CHK-04 | コード | ケース単位 | 1テストケース分のアサーション内容のみで判定できる |
| UT-CHK-05 | コード | ケース単位 | 1テストケース分のアサーションとスキーマ定義の対応関係のみで判定できる |
| UT-CHK-08 | 仕様書 | 全体 | 選定基準の機械的走査は、全実装ファイルを俯瞰しないと判定できない |
| UT-CHK-09 | 仕様書 | 全体 | 実装工程の指摘一覧との突合は、対象一覧全体を俯瞰しないと判定できない |
| UT-CHK-10 | 仕様書 | ケース単位 | 1テストケースの呼び出し値・想定結果のみで判定できる |
| UT-CHK-11 | 仕様書 | 全体 | 新規テストケースの追加漏れ確認は、生成済み全テストケースを俯瞰しないと判定できない |
| UT-CHK-12 | 仕様書 | ケース単位 | 1テストケースの対応設計書リンクのみで判定できる |
| UT-CHK-13 | コード | ケース単位 | 1関数のdocstring・型ヒントのみで判定できる |
| UT-CHK-14 | コード | ケース単位 | モジュール冒頭1箇所の記述のみで判定できる |
| UT-CHK-15 | コード | 全体 | 対応する仕様書の存在確認は、仕様書ファイル一覧との突合が必要で判定できる |
| UT-CHK-16 | コード | ケース単位 | 1ファイルのヘッダー記述のみで判定できる |
| UT-CHK-17 | 仕様書 | ケース単位 | 1テストケースの対象特性（数値比較か要素独立判定か）のみで判定できる |
| UT-CHK-18 | コード | ケース単位 | 1テストケースの入力値のみで判定できる |
| UT-CHK-06 | コード | ケース単位 | 1テストケース分のテスト関数とテスト対象メソッド名のみで判定できる |
| UT-CHK-07 | コード | 全体 | 共通モジュールへの集約状況は、生成済み全テストファイルを俯瞰しないと判定できない |
| UT-CHK-19 | 仕様書 | 全体 | 表記ゆれパターンの網羅は、対象への生成済み全テストケースを俯瞰しないと判定できない |
| UT-CHK-20 | 仕様書 | 全体 | 同じ脅威クラスを持つ複数関数間の横展開状況は、複数ファイルを突き合わせないと判定できない |
| UT-CHK-21 | 仕様書 | ケース単位 | 1テストケースのセル内容のみで判定できる |
| UT-CHK-22 | 仕様書 | 全体 | 成果物全体をレンダリングしないと列数の意図通りの表示を判定できない |

判定範囲分類の内訳は「ケース単位」11件（UT-CHK-04〜06、10、12〜14、16〜18、21）・「全体」11件（UT-CHK-01〜03、07〜09、11、15、19、20、22）。生成対象の内訳は「仕様書」12件（UT-CHK-01〜02、08〜12、17、19〜22）・「コード」10件（UT-CHK-03〜07、13〜16、18）。

なお、フレームワーク固有の落とし穴は`pytest/pytest_単体テスト_チェックリスト.md`を参照する（実装_チェックリスト.mdとFastAPI_実装_チェックリスト.md等の関係と同様、フレームワーク固有版はAIの自己レビューサイクルへは埋め込まず、人手によるレビュー時の参考情報として使用する）。
