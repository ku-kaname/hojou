# コミットルール

## コミットメッセージ形式

```
[type] 対象 内容

詳細説明（必要な場合のみ）
```

- **対象**：ファイル名（拡張子なし）または機能名
- **内容**：体言止め（例：「追加」「修正」「整理」）
- **文字数**：50文字以内

---

## コミット・PR・Issueの粒度

コミットは細かく、PRとIssueは関連する作業をまとめる単位で切る。

| 単位 | 粒度 |
|---|---|
| **コミット** | 1指摘・1ファイル・1関数など細かく |
| **PR** | 関連する複数コミットをまとめる（含めてよい変更の範囲は[Issueルール](Issueルール.md)の「PRに含める変更」参照） |
| **Issue** | PRと1対1 |

```
Issue: レビュー指摘対応（CRUD/ユーザー操作）
  └── branch: feature/XX
        ├── commit: [fix] ユーザー作成 指摘No.1 現在日時取得をmainへ移動
        ├── commit: [fix] ユーザー情報削除 指摘No.1 返り値の型をUser|Noneに修正
        └── commit: [fix] ユーザー情報更新 指摘No.1 返り値の型をUser|Noneに修正
  └── PR → merge → Issueクローズ
```

### コミット粒度の基準

| 作業種別 | 粒度 |
|---|---|
| 設計書の新規作成 | 1ファイル1コミット |
| レビュー指摘対応 | 1指摘1コミット（複数ファイルにまたがっても） |
| コードの追加・修正 | 1エンドポイント or 1関数単位 |
| 設計書とコード | 必ず別コミット |

## タグ一覧

| タグ | 用途 | 例 |
|---|---|---|
| `[add]` | 新規ファイル・機能の追加 | `[add] ユーザー作成設計書を格納` |
| `[fix]` | 誤り・バグの修正（レビュー指摘対応含む） | `[fix] ユーザー作成 指摘No.1 現在日時取得をmainへ移動` |
| `[update]` | 誤りではない変更・仕様追加・拡張 | `[update] ユーザー作成 引数にtoday追加` |
| `[refactor]` | 動作変更を伴わないコードの整理 | `[refactor] crud.py ユーザー作成処理を整理` |
| `[test]` | テストの追加・修正 | `[test] ユーザー作成エンドポイントのテスト追加` |
| `[chore]` | 環境設定・依存パッケージ等 | `[chore] requirements.txtを更新` |

---

## `[fix]` と `[update]` の使い分け

| ケース | タグ |
|---|---|
| 設計書の誤り修正（レビュー指摘対応） | `[fix]` |
| コードのバグ修正 | `[fix]` |
| 誤りではないが仕様変更・追記が必要 | `[update]` |
| 機能拡張・新しい引数の追加 | `[update]` |

---

## レビュー指摘対応コミットの書き方

指摘番号をメッセージに含めることで `git log` による追跡を可能にする。

```
[fix] ユーザー作成 指摘No.1 現在日時取得をmainへ移動
```

詳細が必要な場合は2行目以降に記載する。

```
[fix] ユーザー作成 指摘No.1 現在日時取得をmainへ移動

- crud内部でdatetime.now()を呼んでいた箇所をmain側に移動
- today引数としてcrudに渡す設計に統一
```

## AIによる追跡

以下のコマンドでAIエージェントも変更履歴を追跡できる。

```bash
# 特定ファイルの履歴
git log --follow --oneline <ファイルパス>

# 差分も含めて確認
git log --follow -p --oneline <ファイルパス>

# 指摘番号で検索
git log --oneline --grep="指摘No.1"
```

リネームをまたいで履歴を追跡するため `--follow` を必ず付けること。
