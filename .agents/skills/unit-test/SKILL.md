# 単体テストの考え方

- テスト仕様書はテンプレートを基に作成すること
- 費用対効果の考えから、「簡単な処理→DB接続→簡単な処理」という単純なフローについては結合テストで実施する。
- ただし、条件分岐が複雑なものはモックを利用した単体テストを追加することを検討する。
- 「複雑」の定義については、以下のいずれかに当てはまるものである。これらが検討対象になる。
    - if文（for文、while文含む）で3つ以上の条件で判定している。
    - if文（for文、while文含む）が2階層以上（入れ子構造）になっている。
    - 設計書、および実装にて条件箇所の指摘を受けている。
    - 再帰処理を行っている。
    - 数式を用いた計算を行っている。
- その他、ユーザーが単体テストを行うべきだと判断したものについても実施する。
- テスト疎通のために実装を修正した場合、設計書と実装が一致することを確認する。
- 設計書と実装が乖離した場合、レビュー工程の作業順に従って修正を行う。

---

## 作業手順
1. 設計書の確認
2. 単体テスト仕様書作成
    - 単体テストの考え方に基づき、実施要否を判断する。
    - 設計書及び実装の処理に対応するようテスト仕様書を作成する。
    - `design`スキルのサンプル処理記述書（復習項目更新）を基に作成した例は`references/サンプル/復習項目更新_単体テスト仕様書.md`に格納している。
3. チェックリストを確認し、問題があればレビュー工程前なのでそのまま修正可能。
4. 単体テスト仕様書レビュー工程
    - `運用ルール/開発ルール/レビュー工程ルール.md`に従う。
5. 単体テストコード作成
    - ユーザーはシステム作成の知識がないことを前提に、テストコードには分かりやすくコメントを付与すること。
    - テストコードは、「## テストコードの形式」に従って記載すること。
6. 単体テストコードレビュー工程
    - `運用ルール/開発ルール/レビュー工程ルール.md`に従う。
7. テスト実行
    - エラーがあれば指摘表を記載して修正する。

## テストコードの形式
- ファイルの冒頭（import文がある場合はその後）に、ヘッダーとして以下を記載する。
    - 機能論理名
    - テスト対象ファイル
    - テスト対象クラス（クラスがない場合は`-`）
    - テスト対象メソッド
    - テスト仕様書（格納パス）
- テスト関数ごとに、関数の直前に、単体テスト仕様書の項番と詳細を記載する。
- テスト関数名は、`test_<テスト対象メソッド名>_<項番（3桁）>_<内容>`とする。
- Python以外の言語も、その言語のコメント記法で、同じ項目を記載する。

以下はPython（pytest）の例。
```python
from app.services import update_review_item

# ==================================================
# 復習項目更新
# テスト対象ファイル：services.py
# テスト対象クラス：-
# テスト対象メソッド：update_review_item
# テスト仕様書：テスト仕様書/単体テスト仕様書/サーバー処理/復習項目操作/復習項目更新_単体テスト仕様書.md
# ==================================================

# ========== 単体テストNo.4 ==========
# 復習項目のみ指定した場合、update_reviewのみ呼ばれupdate_review_managementとupdate_all_review_managementが呼ばれないこと
def test_update_review_item_004_review_item_only(mocker):
    ...
```
