# ブランチルール

## 新規開発時（v1.0.0以前）
- ブランチはIssue作成後、`origin/main`を起点に作成する。
- `origin/main`への直接pushは禁止し、Issueに紐づく作業ブランチからPRを作成してマージする。
- 既存の作業ブランチで作業を再開する場合、再開前に必ず`origin/main`に追加された未取り込みコミットの有無を確認する。
- 乖離がある場合は、作業再開前に`origin/main`の変更を作業ブランチへ取り込む。

## 新規開発完了時（v1.0.0になったタイミング）
- v1.0.0の公開後、`main`を公開済み成果物を保持する公開用ブランチとする。
- v1.0.0の公開時、`main`の該当コミットにタグ`v1.0.0`を付与する（書式は「公開時」参照）。
- `origin/main`を起点に`dev`ブランチを作成し、リモートリポジトリへpushする。
- `dev`は次回公開予定の成果物を統合する開発用ブランチとし、以降削除しない。
- v1.0.0以降、通常の開発では`main`を起点に作業ブランチを作成しない（例外は「Hotfix」参照）。
- `main`および`dev`への直接pushは禁止する。

## 改修時（v1.0.0以降）
- ブランチはIssue作成後、`origin/dev`を起点に作成する。
- 1バックログにつき1つの作業ブランチを作成する。
- 作業ブランチのPRは`dev`をマージ先とする。
- 既存の作業ブランチで作業を再開する場合、再開前に必ず`origin/dev`に追加された未取り込みコミットの有無を確認する。
- 乖離がある場合は、作業再開前に`origin/dev`の変更を作業ブランチへ取り込む。

## 公開時（v1.0.0以降）
- 公開対象の変更が`dev`に揃った時点で、`dev`から`main`へのリリースPRを作成する。
- リリースPRには、`dev`と`main`の差分として次回公開対象となる変更をまとめて含める。
- リリースPRを`main`へマージすることで公開版を更新する。
- `dev`から`main`へのリリースPRは、通常の「1バックログ＝1Issue＝1作業ブランチ＝1PR」の対応関係には含めない。
- リリースPRを`main`へマージした後、`main`の該当コミットにバージョンタグ（システムのバージョン）を付与する（v1.0.0から付与し、v1.0.0より前は付与しない）。
- バージョン（上げ幅）は[バージョン管理ルール](../開発ルール/バージョン管理ルール.md)の基準を目安に、人が判断する（AIは提案のみ）。
- 一度付与したタグは付け替え・削除・移動をしない。
- タグ名は、SemVerの番号`MAJOR.MINOR.PATCH`に接頭辞`v`を付けた`vMAJOR.MINOR.PATCH`とする。
- 付与したタグは、リモート（`origin`）へpushする。
```bash
git tag -a vMAJOR.MINOR.PATCH -m "Release vMAJOR.MINOR.PATCH"
git push origin vMAJOR.MINOR.PATCH
```

## Hotfix（v1.0.0以降、緊急修正時）
- 原則として、`main`を起点とした作業ブランチの作成は禁止する。
- ただし、公開済みバージョンに対する緊急修正が必要な場合は、例外として`origin/main`を起点にHotfix用ブランチ（`hotfix/<issue番号>`）を作成できる。
- HotfixもIssueを作成し、「1バックログ＝1Issue＝1作業ブランチ＝1PR」の原則に従う。
- HotfixのPRは`main`をマージ先とする。
- `main`へのマージ後、システムのバージョンを更新して`main`の該当コミットにタグを付与し、`origin`へpushする（手順は「公開時（v1.0.0以降）」と同じ）。上げ幅は通常PATCHだが、人が判断する（[バージョン管理ルール](../開発ルール/バージョン管理ルール.md)参照）。
- Hotfixの内容は、必ず`dev`にも反映する（`dev`への直接pushは禁止のため、PR経由で行う）。
