# レビュー工程ルール

要件定義書・設計書・実装・テスト仕様書・テストコードなど、各工程の成果物に対するレビュー工程は、以下の共通手順で運用する。レビュー工程以降は、成果物を修正する前に必ずレビュー指摘表へ記載しなければならない。

ここでいう指摘とは、成果物の誤り・不備の指摘を指す。仕様変更・仕様追加など誤りではない変更は指摘には当たらないため、レビュー指摘表には記載せず、引継ぎ資料（[引継書ルール](../引継書ルール/引継書ルール.md)に従い、機能別引継書またはタスク毎引継ぎ資料）にのみ記録する。

## 手順

1. レビュー指摘表作成
    - [テンプレート](テンプレート/レビュー指摘表_テンプレート.md)を参考に作成する。
    - 格納先：`レビュー指摘表/<工程名>/<レビュー対象と同じフォルダ構成>/`（工程ごとの格納先は下表を参照）
        - 例：設計書が`設計書/05_ビジネスロジック処理/成果物/設計書生成_v0.1.0.md`の場合
          → `レビュー指摘表/設計工程/05_ビジネスロジック処理/成果物/設計書生成_v0.1.0_レビュー指摘表.md`
    - コード（実装コード・テストコード）の指摘表のファイル名は、処理名（論理名）を用いて`<処理名>_レビュー指摘表.md`とする（例：`ユーザー登録_レビュー指摘表.md`）。
    - 該当する成果物だけではなく、影響がある機能群を含めて矛盾が無いよう確認する。
    - 他の機能に影響がある場合には、該当の機能の指摘表に追記する。
2. 引継ぎ資料を作成する（対象範囲・タイミングは[引継書ルール](../引継書ルール/引継書ルール.md)に従う）。
3. レビュー対応
    - 対応完了時に、成果物のバージョンのPATCHを+1する（[バージョン管理ルール](バージョン管理ルール.md)に従う）。
4. 再鑑
    - 追加修正が必要な場合は、その対応完了時にPATCHを+1する（同上）。
5. 再鑑完了後、成果物のバージョンを確定する（互換性に応じてMINORまたはMAJORを+1し、PATCHを0にリセットする。[バージョン管理ルール](バージョン管理ルール.md)に従う）。
6. 引継ぎ資料を更新する（対象範囲・タイミングは[引継書ルール](../引継書ルール/引継書ルール.md)に従う）。

## 工程ごとの格納先

| 工程 | レビュー対象 | 格納先 |
|---|---|---|
| 要件定義工程 | 要件定義書 | `レビュー指摘表/要件定義工程/<要件定義ファイルと同じフォルダ構成>/` |
| 設計工程 | 設計書 | `レビュー指摘表/設計工程/<設計書と同じフォルダ構成>/` |
| 実装工程 | 実装コード | `レビュー指摘表/実装工程/<実装ファイルと同じフォルダ構成>/` |
| 単体テスト工程（仕様書） | 単体テスト仕様書 | `レビュー指摘表/単体テスト工程/<テスト仕様書と同じフォルダ構成>/` |
| 単体テスト工程（コード） | 単体テストコード | `レビュー指摘表/単体テスト工程/<テストコードと同じフォルダ構成>/` |
| 結合テスト工程（仕様書） | 結合テスト仕様書 | `レビュー指摘表/結合テスト工程/<テスト仕様書と同じフォルダ構成>/` |
| 結合テスト工程（コード） | 結合テストコード | `レビュー指摘表/結合テスト工程/<テストコードと同じフォルダ構成>/` |
| プロジェクト改修 | 対象工程の成果物 | `レビュー指摘表/<対象工程>/<対象工程ファイルと同じフォルダ構成>/` |
